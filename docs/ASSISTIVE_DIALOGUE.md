# V7 生活任务的文字与语音对话

`MissionEngine.submit(text, request_id, session_id)` 是网页、CLI 和 ROS 文本订阅回调的共同入口。新增 `assistive_dialogue.py` 将完整句子转成生活服务的结构化 action；数据库写入、记录状态、周历计算和审计仍由 `AssistiveService` 负责。它不直接控制机械，也不把“有人回应了”当作独立验证过的照护结果。

## 可以直接试的完整对话

| 场景 | 指令与后续指令 |
|---|---|
| 提醒知晓 | `0分钟后提醒我喝水` → `确认喝水提醒`；有最近上下文时也可说 `这条提醒我知道了` |
| 稍后再提醒 | `0分钟后提醒我喝水` → `稍后五分钟` → `取消喝水提醒` |
| 多条或同名记录 | 创建两条到时提醒 → `确认提醒` → 听取候选 → `第二个` |
| 改标题和时间 | `十分钟后提醒我喝水` → `把喝水提醒改名为饮水` → `把饮水提醒改到明天上午八点` |
| 改周历 | `把饮水提醒改成每周一和周三上午八点`；`把饮水提醒改为单次` 清除重复规则 |
| 平安等待 | `开始30分钟平安确认` → `我在`；等待期间可用 `取消平安确认` 或 `取消刚才的定时确认` |
| 人工协助的本地回报 | `我需要如厕帮助` → `有人回应了` → `协助已解决`；或 `取消协助请求` |
| 清单勾选与撤销 | `开始晨间清单` → `完成晨间清单第一个项目` → `取消勾选晨间清单第一项` |
| 用品备好 | `把纸巾加入购物清单` → `纸巾已备好` |
| 退出生活候选 | `取消生活选择`，只退出选择，不取消提醒或协助记录 |

提醒必须到时才能确认知晓。语音确认不证明服药、喝水或任何身体动作已完成。用品、清单和人工协助状态均表示用户报告的本地记录；不会自动联系外部人员，也不证明人员已到场。

解析采用完整句式匹配；未支持的改法、否定和多个混合动作不会被拆成部分生活动作执行。表中功能不要求使用模型。新建周历也支持 `每周一和周三上午八点提醒我喝水`，其时区和截止规则参见周历模块文档。

## 会话、候选和重试

- 多个候选先澄清，不根据排序猜测用户意图。最多播报五项，包含序号、名称和有意义的到期时间；超过五项要求补充准确名称。
- 澄清由 `submit` 保存到该 `session_id` 的 SQLite 会话，五分钟后过期。选择序号前重新检查全部候选及快照；增加、删除、改名、改期或状态变化会使旧序号失效，并重新澄清。
- 超过五项、没有匹配项或候选过期后，保留“生活操作待补充”的话题标志，阻止裸确认落入旧机器人计划。该标志没有可执行候选，序号不能选择被省略的记录；明确的新机器人话题、显式确认执行或取消生活选择可以结束它。
- 最近操作的记录按类型保留短期焦点。上次已处理的记录、被替换的记录和新的提醒周期不会被一句重复的泛指答复自动转向下一条；应明确说出准确名称重新选择。
- 同一 `session_id + request_id` 重传返回原始回执；不能把同一请求重新绑定到剩余提醒。相同 request ID 搭配不同文字会被拒绝。
- 生活指令保留尚未确认的机器人计划。生活候选还待选择时，裸 `确认` / `就这样` 会要求选择，不会执行旧机器人草稿；明确的 `确认执行` / `执行计划` 和 `取消计划` 仍属于机器人规划。确认生活提醒请说 `确认提醒`。开始新的机器人话题会清掉旧生活候选，避免后续序号被旧话题截获。
- 清单去重同时检查目标项目是否仍处于所述状态。通过其他入口重置或取消勾选后，新请求可以重新勾选；原 request ID 的重传仍只返回原回执，不会把旧请求重放到重置后的清单。
- 停止、暂停等机械控制优先于生活对话。生活候选不会阻挡停止命令。

会话是对话范围，不是身份认证。网页每个标签页使用独立 session；CLI 可显式指定。现有 ROS String 文本 topic 没有说话人身份字段，因此该节点的文本入口共用默认会话；不能据此声称实现了多人声纹隔离。不同使用者应由上游分配独立会话入口。

## 预览和前端响应

生活 `engine.preview(text, session_id)` 完全只读：不创建记录、不保存候选或焦点、不消耗请求 ID。只有 submit 产生的澄清支持后续口头“第二个”。只读预览中的选项按钮可提交响应给出的完整命令。

返回兼容现有控制台字段：`kind`、`message`、`options`、`needs_clarification`、`needs_confirmation`。`message` 本身包含可播报候选，不需要语音客户端解析 ID。生活记录执行成功仍返回 `assistive: {type, record}`；澄清或无可操作记录时是 `assistive: {type: "dialogue"}`。没有匹配的结果不会创建新记录。

`options` 是可回送的完整字符串，末尾带记录 ID 前缀及快照指纹；前端应原样回送。`option_labels` 与它一一对应，提供无指纹的候选序号、名称及时间作为按钮标签，同名同日期也能由序号区别。旧选项对应记录改变后会被拒绝，不会确认新周期。指纹是并发状态绑定，不是认证凭据。

单条已有记录的预览还返回 `action` 和 `execution_command`。如提供“执行此预览”按钮，应回送 `execution_command`，不要重新提交未绑定的泛指原句。用户重新输入原句属于新指令，需要再次解析当前状态。

## CLI 与 ROS 入口

```sh
python -m robot_voice_patrol --home --db .runtime/dialogue.sqlite3 \
  --command "开始30分钟平安确认" --session-id home-user --request-id waiting-1
python -m robot_voice_patrol --home --db .runtime/dialogue.sqlite3 \
  --command "我在" --session-id home-user --request-id confirm-1
```

上面两次 CLI 调用是不同进程，共享数据库和会话。`--preview` 只预览；无需网页。ROS 节点原有 `command_received` 将文本交给同一 engine，并通过语音输出 topic 返回 message。识别服务只需把最终识别文字送进该入口。

## 已验证的范围

`tests/test_assistive_dialogue_v7.py` 包含 36 项检查，覆盖文字闭环、只读预览、持久澄清、会话隔离、候选变更、空候选及过多候选、周期防误确认、请求去重、清单重置、同名修改、并发重传、控制优先、CLI 真实子进程，以及注入 Python ROS 替身的 `command_received` 回调与候选播报。相关生活、引擎、自然语言、ROS 生命周期替身回归共 150 项通过。

这些是软件执行与接口验证，不包含真实麦克风、语音识别准确率、扬声器播放、原生 ROS/DDS 通信或物理机器人试验。硬件控制链和未接入的厂商驱动边界见 `HARDWARE_GATEWAY.md`。
